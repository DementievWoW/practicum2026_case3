# Q&A · Архитектура и принцип системы (общая часть)

100 вопросов с короткими ответами. Используем на выступлении и QA-сессии.

## Задача и постановка (1–10)
**1.** Что делает система? — Принимает NL-запрос, генерирует PostgreSQL-SQL по схеме заказчика и аудирует на безопасность; возвращает одобренный SQL + полный audit-log.
**2.** Кто заказчик? — GreenData (платформа управления распределёнными данными).
**3.** Какая БД? — PostgreSQL. Схема — 60 таблиц (срез из ~201 в полной БД заказчика).
**4.** Почему система не исполняет SQL? — Прямое требование ТЗ: «цикл завершается одобрением судьи или исчерпанием лимита». Исполняет сам заказчик.
**5.** Какие 9 классов уязвимостей покрываем? — SQL_INJ_CLASSIC, SQL_INJ_UNION, SQL_INJ_TIME, DML_NO_WHERE, PRIV_ESCALATE, PLPGSQL_UNSAFE, DIRECT_SENSITIVE, SELECT_STAR, NO_PAGINATION.
**6.** Что такое RISK_THRESHOLD? — Порог 4.0 по шкале 0–10; ниже него — approved.
**7.** Сколько итераций цикла? — DEFAULT_MAX_ITERATIONS=5; не сошлось — выходим с последним вариантом и approved=False.
**8.** Что в audit_log? — Все итерации: SQL, найденные уязвимости с risk_score, вердикт судьи, правки.
**9.** Что такое DIRECT_SENSITIVE? — Прямой SELECT/SHOW колонок с PII (паспорта, СНИЛС, карты, пароли); 152-ФЗ.
**10.** Почему PLPGSQL отдельным классом? — Бонус ТЗ: динамический SQL внутри функций (EXECUTE) + SECURITY DEFINER — отдельная семантика.

## Высокоуровневая архитектура (11–20)
**11.** Один LLM или несколько? — Гибрид: LLM-генератор + LLM-судья + детерм. правила + ML-классификатор + RAG.
**12.** Почему не одна большая модель «реши всё»? — Дороже, объяснимость хуже, синтаксис ловят правила за миллисекунды.
**13.** Из каких компонентов? — Schema layer, Генератор, Reflector, Судья (Phase 1+1.5+2), Оркестратор, Инфраструктура.
**14.** Поток запроса? — task → schema linking → промпт → LLM → SQL → судья → агрегатор risk → approved? → result; иначе → reflector → промпт ↻.
**15.** Что входит в Schema layer? — Парсер DDL → schema_catalog → карточки → эмбеддинги → FAISS-индекс.
**16.** Зачем reflector? — Превращает findings судьи в «урок», который инжектится в промпт следующей итерации (in-context Reflexion).
**17.** Чем reflexion отличается от RLHF? — Не трогает веса; меняет промпт. Адаптация в рантайме.
**18.** Что такое walking skeleton? — Каркас системы с настоящим циклом и контрактами, но с заглушками вместо реальных компонентов; заменяются по одному, не ломая интерфейсы.
**19.** Что критично в архитектуре? — Контракт baseline (от заказчика) + Protocol-интерфейсы (LLMClient, Tracer, Database) + цикл с лимитом и логом.
**20.** Что хранится между итерациями? — sql_history, audit_feedback (последний AuditResult), reflection (список Lesson, окно 5).

## Цикл и инвариант (21–30)
**21.** Когда цикл останавливается? — `audit.approved=True` (risk<4.0) или iter>max_iterations.
**22.** Что если не сходится за 5? — Возвращаем последний SQL с approved=False; юзер сам решает или эскалация.
**23.** Почему 5 итераций? — Эмпирически: больше — потери токенов, на сложных кейсах за 3–4 уже выходит, 5 — буфер.
**24.** Что модель «учит» между итерациями? — Уроки в промпте, не веса. In-context, на следующий запрос не переносится (если не персистим).
**25.** Reflection — это одна строка или объект? — `Lesson(rule_id, error_description, recommendation)`; до 5 в окне.
**26.** Что выгоднее: больше итераций или сильнее модель? — Сильнее модель → больше approved с первой попытки; больше итераций → ловит edge cases.
**27.** Судья может ошибаться? — Да: FP (отбросил корректный) и FN (пропустил уязвимый). FP лечится reflection-спором; FN — правилами Phase 1.
**28.** Reflexion синхронный? — Да, прямо после judge, перед следующей итерацией.
**29.** Если findings пусто? — Reflection не пишется; цикл выходит по approved.
**30.** Если уроки противоречат? — Reflector делает дедуп по rule_id и предпочитает свежий + более конкретный.

## Walking skeleton и контракты (31–40)
**31.** Что в baseline-контракте? — dataclasses Vulnerability, AuditResult, IterationLog, SystemResult; классы SQLGenerator, SecurityAuditor, SQLSecuritySystem; функция run_sql_security_pipeline. Мы это НЕ трогаем.
**32.** Почему не трогаем baseline? — Это контракт заказчика, по нему оценивают.
**33.** Где наши классы? — В `src/case3/` — наследники/реализации интерфейсов baseline.
**34.** Что такое Protocol? — Python typing.Protocol — структурный тайпинг без наследования. LLMClient, Tracer, Database — Protocols.
**35.** Почему Protocol, а не ABC? — Меньше связности; реальный langfuse SDK уже годится как Tracer без обёрток.
**36.** Как подменить мок на реал? — Передать другой инстанс (`llm=`, `tracer=`). Код вокруг не меняется.
**37.** Где MockLLMClient? — `src/case3/llm/mock.py`. scenario="evolve"/"always_good"/"always_bad".
**38.** Что делает scenario="evolve"? — Первый прогон — «грязный» SQL, после уроков — «чистый». Имитирует рефлексию.
**39.** Зачем три сценария? — Тесты: evolve — нормальный цикл; always_bad — проверка лимита; always_good — happy-path.
**40.** Почему baseline без LangGraph? — Заказчик не фиксировал framework; на MVP — Python-цикл, LangGraph — задел.

## Безопасность и ТЗ (41–50)
**41.** Почему нельзя исполнять SQL? — Цитата ТЗ + риск порчи прод-данных. Только EXPLAIN-эвристика.
**42.** EXPLAIN в моке — насколько точно? — Фейк по эвристикам (seq scan/cartesian). Реальный EXPLAIN — на песочнице с тем же data_model.sql + faker.
**43.** Почему нельзя EXPLAIN ANALYZE? — Он исполняет запрос. Без ANALYZE — план без выполнения.
**44.** 152-ФЗ — что соблюдаем? — Не извлекаем PII в литералах SELECT; не сохраняем плейн-PII в логах; sensitive-детектор флагит выгрузки.
**45.** Что если попросят DROP TABLE? — R-PRIV_ESCALATE: DDL без явного разрешения → risk 10.
**46.** Кто решает «уровень доступа»? — На уровне БД пока не моделируем. ТЗ требует флагить попытки повышения привилегий.
**47.** Хранится ли user_id? — В IterationLog не пробрасываем (privacy); в Langfuse — да.
**48.** RAG-база содержит секреты? — Нет, только публичные CWE/CAPEC/OWASP и наши уроки.
**49.** Можем ли слить схему? — Карточки таблиц видны только генератору в промпте; в публичных логах — только имена.
**50.** Лицензионные нюансы? — pglast GPLv3 — нужно решение по дистрибуции (sqlglot Apache как fallback).

## Команда и зоны (51–60)
**51.** Кто что делает? — Уч.1: парсер + фронт; Уч.2: аудитор; Уч.3: LLM; Уч.4: оркестратор + датасет + инфра.
**52.** Какие зоны на моках? — LLM генератор/судья (mock.py), парсер (заглушка), 7 правил аудитора TODO, reflector (детерм. таблица), эмбеддинги и FAISS.
**53.** Что реально готово? — Оркестратор + цикл + контракты, инфра (метрики, трейсинг, БД), агрегатор риска, decision-логика, dedup, schema-models, 2 правила.
**54.** Что в зоне Уч.4 кроме инфры? — Оркестрация, контракты, датасет (back-translation, sensitive overlay), schema-models.
**55.** Кто пишет промпт? — Уч.3.
**56.** Кто пишет CodeBERT? — Уч.2.
**57.** Кто за датасет? — Уч.4: 14 seed-examples + back-translation + sensitive overlay.
**58.** Что если кто-то опоздал? — Заглушка живёт, цикл крутится. Поэтому walking skeleton.
**59.** Где границы зон в коде? — По папкам: `schema/parser.py` (Уч.1), `audit/*.py` (Уч.2), `nodes/generator.py`+`reflector.py` (Уч.3), `pipeline.py`+`infra/*`+`dataset/*` (Уч.4).
**60.** Как меряем прогресс? — Кол-во ⬜→🟢 в `target_components`; покрытие правил Phase 1.

## Технологии (61–70)
**61.** Какие модели? — Qwen2.5-Coder-32B (генератор), Qwen2.5-7B (судья), CodeBERT (Phase 1.5).
**62.** Почему Qwen, а не Llama? — На coder-задачах Qwen-Coder выше на Spider/BIRD, Apache-лицензия.
**63.** Почему 32B? — Баланс качества и стоимости. 70B+ — переплата для SQL.
**64.** Почему 7B для судьи? — Триаж и объяснение — простая задача; разделение моделей дешевле, чем self-critique 32B.
**65.** Какая квантизация? — AWQ-4bit для серве: ~20 GB VRAM, near-FP16 качество.
**66.** Где хостим LLM? — vLLM/Colab/OpenAI-compatible эндпоинт (через `LLM_BASE_URL`).
**67.** Эмбеддинги? — multilingual-e5 (или bge-m3 по флагу `HF_EMBEDDING_MODEL`).
**68.** Почему e5/bge? — Поддержка русского; топ MTEB на retrieval.
**69.** Векторный индекс? — FAISS in-memory (60 векторов — мгновенно).
**70.** Где хранить продакшен-вектора? — На 60 — FAISS-flat хватит; для большого RAG — qdrant/pinecone.

## Метрики качества (71–80)
**71.** Какие метрики оцениваем? — approved-rate, среднее число итераций, риск-trajectory, FP/FN судьи, латентность p95.
**72.** Главная бизнес-метрика? — Execution Accuracy + доля проходящих аудит, приближённая на нашем sandbox.
**73.** Что такое Execution Accuracy? — Доля запросов, чей результат совпадает с эталоном на тестовой БД.
**74.** Почему не Exact Match? — Один результат можно написать разным SQL; EM штрафует валидные альтернативы.
**75.** Как меряем безопасность? — Recall (доля пойманных уязвимостей) и precision судьи на размеченном датасете.
**76.** Что такое risk_trajectory? — Список risk_score по итерациям. Хорошая сходимость — монотонно вниз.
**77.** Если risk сразу 0 — подозрительно? — Да: проверяем, что задача нетривиальна (не игрушка для мока).
**78.** Сколько уязвимостей в датасете? — 14 seed + back-translation + sensitive overlay.
**79.** Где dashboard? — Grafana «SQL Security» (порт 13000).
**80.** Что трейсим в Langfuse? — Один trace на запрос: спаны generate/audit/reflect, скоринги final_risk и approved.

## Масштабирование и прод (81–90)
**81.** Сколько RPS на MVP? — На моках — десятки/сек; узкое место — LLM (секунды на токен).
**82.** Как масштабировать LLM? — vLLM continuous batching: одна модель = N конкурентных запросов в один проход.
**83.** Нужен ли gRPC? — Только если выберем Triton. Через vLLM хватает OpenAI-compatible HTTP.
**84.** Нужен ли k8s? — На MVP — нет (compose). В проде — да: автоскейл worker-подов, GPU-пулы.
**85.** CPU-GPU split? — Оркестратор и аудитор — CPU; модели — GPU. На 2 ГБ VPS реально только CPU-часть.
**86.** Резервируем модель? — В проде — 2+ реплики vLLM за балансером.
**87.** Что если LLM упал? — Fallback на правила (всегда работают) + статус «деградация» в Langfuse.
**88.** Как версионируем модель? — env LLM_MODEL=qwen/qwen-2.5-coder-32b-instruct; хешим в трейсе.
**89.** Что если меняется ТЗ? — Контракт baseline тот же; обновляем правила/RAG/уроки.
**90.** Как обновляем датасет? — Дописываем в `seed_examples.py` + back-translation добивает синтетику.

## Эволюция и риски (91–100)
**91.** Что добавим первым? — Реальный Qwen вместо мока + полный набор правил + CodeBERT.
**92.** LangGraph когда? — После стабилизации Python-цикла: PostgresSaver для checkpoint и time-travel.
**93.** Файнтьюн? — Только если данных ≥10K. Сейчас — in-context Reflexion.
**94.** Risk #1? — LLM-судья ложно отбрасывает корректный SQL → теряем юзкейсы. Митигация: правила-«easy yes», LLM только для сложных.
**95.** Risk #2? — Reflector «зацикливается» на одной правке. Митигация: окно 5 уроков, дедуп.
**96.** Risk #3? — Маленький датасет → плохое обобщение. Митигация: back-translation + sensitive overlay + 9 классов.
**97.** Юридический риск? — 152-ФЗ для PII; pglast — GPLv3 (нужна проверка лицензии).
**98.** Что делать при out-of-schema запросе? — Reflector добавляет урок «таблицы X нет», UI просит уточнение.
**99.** Поддержка не-PostgreSQL? — Не на MVP; адаптация — отдельный парсер + переписать правила.
**100.** Что покажет демо? — Реальный прогон NL→SQL с траекторией risk 5.0→0.0, дашборд Grafana, трейс в Langfuse, `./setup.sh` для коллег.
