# Q&A · Генератор SQL + Reflection-loop · Участник 3

100 вопросов про LLM-генератор, промпты, few-shot, reflection и хостинг моделей.

## Задача NL→SQL (1–10)
**1.** Что генерируем? — PostgreSQL SQL по NL-запросу.
**2.** Входы генератора? — task (NL), top-K таблиц из linking, few-shot, lessons, история SQL.
**3.** Выход? — Один корректный SQL-стейтмент.
**4.** Multi-stmt? — На MVP — нет; план — WITH/CTE.
**5.** Формат? — SQL текстом, без markdown.
**6.** Если LLM вернул JSON/markdown? — Постпроцессинг чистит ```sql … ```.
**7.** Запрос на ALTER? — Вне MVP — отдаём предупреждение.
**8.** Если запрос неоднозначен? — Reflector добавляет clarifying-урок; на UI спрашиваем.
**9.** Несколько SQL подходят? — Возвращаем первый; в audit_log вся история.
**10.** Не-PostgreSQL диалекты? — Не на MVP; план — отдельный парсер-маппер.

## Модель (11–20)
**11.** Модель? — Qwen2.5-Coder-32B-Instruct.
**12.** Tokenizer? — Qwen tokenizer (~150K vocab).
**13.** Context? — 128K (наши промпты — 4–8K).
**14.** Stop tokens? — `;`, `\n\n`, custom delimiter.
**15.** Температура? — 0.0–0.2 на проде (детерминизм); 0.7 при генерации синтетики.
**16.** Top-p? — 0.95.
**17.** Max new tokens? — 1024; обычный SQL — 200–400.
**18.** Формат промпта? — Chat: system + user + assistant placeholder.
**19.** JSON mode? — Не используем — нужен plain SQL.
**20.** Если выход не SQL? — Постпроцессинг + retry с уроком «верни только SQL».

## Промпт-инжиниринг (21–30)
**21.** Структура промпта? — System: «PostgreSQL-эксперт» + правила; User: схема (top-15 + FK) + few-shot + уроки + NL.
**22.** Что в system? — Стиль (no SELECT *, use LIMIT, fully-qualified names), без воды.
**23.** Длина system? — ~300 токенов.
**24.** Где правила безопасности? — В system + в lessons; общие — system, адресные — lessons.
**25.** Зачем дублировать? — Lessons адресные после ошибки, system — общий гайд.
**26.** Сколько few-shot? — 3–5.
**27.** Откуда few-shot? — Retrieval по сходству NL (BM25/dense).
**28.** Чем нормирован промпт? — Жёсткий шаблон: «### Schema», «### Examples», «### Lessons», «### Task».
**29.** Multi-turn vs single? — Single-turn на итерацию; история между итерациями — в lessons.
**30.** Counterfactual examples? — Не используем (дорого по токенам).

## Schema linking-использование (31–40)
**31.** Что подаётся в промпт? — Сокращённое DDL: имя+тип+комментарий; FK — стрелкой; без INDEX.
**32.** Зачем DDL, а не карточка? — Генератору нужны точные сигнатуры (типы, имена), карточка теряет точность.
**33.** Если таблицы нет в подмножестве? — Reflector добавляет урок «таблица X отсутствует».
**34.** Сколько таблиц? — 15 + FK-closure (макс 20–25).
**35.** Сколько токенов на блок схемы? — 1–3K.
**36.** Можно сжать DDL? — Можно: убрать typing если очевидно; на MVP — не сжимаем.
**37.** Что в FK-секции? — Стрелки `client_id → clients(id)`.
**38.** Где код сборки? — `nodes/generator.py::_build_schema_block`.
**39.** Если ширина (50+ колонок)? — Триммим до 20 наиболее «связанных» (через embedding запроса).
**40.** Передаём ли индексы/PK? — Только PK (помогает с уникальностью); индексы — нет.

## Few-shot retrieval (41–50)
**41.** Размер банка? — 14 seed + 100+ синтетика (back-translation).
**42.** Где банк? — `dataset/seed_examples.py` + `dataset_v1.jsonl`.
**43.** Как выбираем? — Эмбеддинг NL → косинус с банком → top-3.
**44.** Зачем few-shot? — Стиль, формат, типичные паттерны (LIMIT, alias).
**45.** Class-balanced few-shot? — На MVP нет; план — balance по vuln-class.
**46.** Когда вредно? — Если все примеры с SELECT * → воспроизведёт. Поэтому seed чистые.
**47.** Многоязычность? — NL на русском (наш домен).
**48.** Контаминация? — Seed не пересекается с test-датасетом.
**49.** Если retrieval даёт ересь? — Fallback на дефолтные top-static.
**50.** Размер few-shot блока? — 1–2K токенов.

## Reflection-loop (51–60)
**51.** Что такое урок? — `Lesson(rule_id, error_description, recommendation)`.
**52.** Кто создаёт? — Reflector — детерм. лук-up (заглушка) → план: LLM/T5.
**53.** Сколько уроков в промпте? — До 5 (окно).
**54.** Где в промпте? — Между few-shot и task: «### Lessons from previous iterations».
**55.** Дедуп? — Да, по rule_id (один класс не дублим).
**56.** Если уроки противоречат? — Свежий выше старого; противоречие → flag в Langfuse.
**57.** Уроки между запросами? — На MVP — нет; план: per-user банк.
**58.** In-context vs RAG? — In-context: урок в промпт; RAG: урок ищется. Мы пока in-context.
**59.** Чем меряем «улучшение»? — Δ risk_score между итерациями.
**60.** Когда reflector «опускает руки»? — После 5 итераций; финальный SystemResult.approved=False.

## Квантизация и хостинг (61–70)
**61.** Квантизация? — AWQ-4bit для генератора; FP16 для эмбеддингов.
**62.** Почему AWQ, а не GPTQ? — Часто быстрее на vLLM, меньше потери на coder.
**63.** Качество AWQ vs FP16? — ~1–2% pass@1 на coder (приемлемо).
**64.** Хостинг? — vLLM (OpenAI-compatible) на GPU; локально — Colab/MCP в dev.
**65.** Continuous batching? — Да: одна модель = N конкурентных запросов в один проход.
**66.** RPS Qwen-32B-AWQ на A100? — ~5–10/сек при 500 токенах выхода.
**67.** Latency p50? — 1–3 сек на 500 токенов.
**68.** Latency p99? — 5–10 сек (cold-start, длинный промпт).
**69.** Cold start? — ~30 сек на загрузку модели в VRAM.
**70.** Замена на сторонний API? — Да: OpenAI-compatible (OpenRouter, Together) — через `LLM_BASE_URL`.

## Hallucinations и качество (71–80)
**71.** Какие галлюцинации типичны? — Несуществующие колонки/таблицы; неверные JOIN; неправильные функции (NOW vs CURRENT_TIMESTAMP).
**72.** Как ловим? — Парсер аудитора + сверка имён с каталогом; reflector делает урок.
**73.** Self-consistency? — Не на MVP (дорого); план — N samples → majority SQL.
**74.** Constrained decoding? — В перспективе — grammar-guided через outlines.
**75.** Chain-of-thought? — Не показываем юзеру; модель «думает» в скрытых токенах.
**76.** «### Plan» секция перед SQL? — Опц. — улучшает на сложных JOIN-ах.
**77.** Параллельная генерация N? — Не на MVP (скорость).
**78.** Repair-model? — Нет; reflection покрывает кейс.
**79.** Pass@1 на нашем датасете? — Цель ≥0.7 простые, ≥0.5 сложные.
**80.** Регрессии? — При смене модели — прогон по seed_examples + synth-set.

## Метрики и риски (81–100)
**81.** Главная метрика генератора? — Execution Accuracy на sandbox.
**82.** Латентность? — p95 < 5 сек (с 1 итерацией).
**83.** Сходимость? — Доля approved за 1 итерацию (цель ≥70%); за ≤3 (цель ≥90%).
**84.** Стоимость на запрос? — N токенов × N итераций × цена/токен; на собственном vLLM — почти 0.
**85.** Что мониторим? — sqlsec_iterations, sqlsec_latency, доля approved.
**86.** Когда заменить модель? — Если pass@1 ниже target или нашлась лучше под лицензию.
**87.** Можно ли учить на наших данных? — Да: LoRA на back-translation. Roadmap.
**88.** Файнтьюн на 14? — Бесполезно; нужно ≥1K.
**89.** Дистилляция 32B→7B? — План L2.
**90.** Модель «упрямится»? — Расширить lessons + few-shot с правильным паттерном.
**91.** Prompt-injection защита? — Юзер-вход санитизируется (no triple-backticks/инструкции); system жёсткий.
**92.** Если NL содержит SQL? — Reflector детектит и игнорит SQL как намерение, тянет смысл из NL.
**93.** NL с PII? — Sensitive-детектор флагит; не сохраняем плейн в логи.
**94.** LLM упал? — Fallback: правила-only режим + «не одобрено за 0 итераций» + просьба повторить.
**95.** Timeout? — LLM_TIMEOUT=120 сек.
**96.** Streaming в UI? — Да, SSE; токены приходят по мере генерации.
**97.** Reproducibility? — seed=42 + T=0 → детерминизм (почти).
**98.** Промпт-кэш? — vLLM prefix cache: одинаковый schema-блок кэшируется → +30% throughput.
**99.** Что в Langfuse? — Input prompt, output SQL, токены, латентность, модель, scoring.
**100.** Что демонстрирует Уч.3? — Трейс в Langfuse: спаны generate, видна reflection-петля, risk-trajectory 5.0→0.0 за 2 итерации.
