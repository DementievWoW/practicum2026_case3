# Q&A · Schema layer · Участник 1

100 вопросов о парсере DDL, каталоге, карточках, эмбеддингах, FAISS и фронте.

## Входной DDL (1–10)
**1.** Что такое DDL? — Data Definition Language: CREATE TABLE, INDEX, FK, COMMENT.
**2.** Где входной DDL? — `data_model_sql/data_model.sql`, 657 KB.
**3.** Сколько CREATE TABLE? — 60.
**4.** Сколько REFERENCES? — 201 уникальное имя в FK.
**5.** Откуда «164 missing»? — 201 (упомянутых) − 37 (пересечение с 60 созданными) = 164 (только в ссылках, без CREATE).
**6.** Почему так? — DDL — срез прод-БД заказчика; полная схема ~200+.
**7.** FK активны в DDL? — Нет, закомментированы `-- ADD CONSTRAINT fk_…`. PK активны.
**8.** Почему FK комментированы? — Заказчик прислал начальную часть — не все ссылочные таблицы вошли.
**9.** Что подтверждаем заказчику? — Это срез; полный список в `docs/customer_qa/schema_coverage.md`.
**10.** Чем это влияет? — Нельзя строить полный FK-граф; FK-замыкание ограничено известными 60.

## Парсер DDL (11–20)
**11.** Чем парсим? — Сейчас regex (заглушка); цель — pglast (полный AST PostgreSQL).
**12.** Почему сейчас regex? — Walking skeleton; pglast — GPLv3, требует решения по лицензии.
**13.** Что вытаскиваем? — Имя таблицы, колонки (имя+тип+комментарий), PK, FK (даже из комментариев), COMMENT ON.
**14.** Что игнорим? — VIEW (пока), CREATE FUNCTION (отдельно для PLPGSQL), INDEX (только имя).
**15.** Куда складываем? — `SchemaCatalog` (dict-like, name → Table).
**16.** Что с COMMENT ON COLUMN? — Парсим и кладём в Column.comment — критично для эмбеддинга карточки.
**17.** Что если синтаксис нестандартный? — В заглушке — падаем тихо; на pglast — точный AST + исключение.
**18.** Скорость парсера? — Для 657 KB: секунды (regex), миллисекунды (pglast).
**19.** Парсим ALTER TABLE? — План: да, инкрементальный патч каталога.
**20.** Кэш парсинга? — Да: persist schema_catalog в JSON, ребилд по хешу DDL.

## Каталог (21–30)
**21.** Что такое schema_catalog? — `SchemaCatalog` — словарь Table-объектов с методами get(), fk_closure(), stats(), to_dict()/from_dict().
**22.** Поля Table? — name, columns (list[Column]), primary_keys, foreign_keys, comment.
**23.** Поля Column? — name, type, nullable, default, comment, is_pk, is_fk.
**24.** Зачем хранить comment? — Бизнес-описание («номер договора кредита»); эмбеддинг карточки на этом держится.
**25.** Размер каталога в памяти? — 60 таблиц × ~30 колонок × ~100 байт ≈ 180 KB.
**26.** Что делает fk_closure()? — По стартовому списку таблиц проходит по FK и добавляет соседей.
**27.** to_card()? — Table.to_card() строит текст: «имя · комментарий · колонки c комментариями».
**28.** Зачем такой формат карточки? — Эмбеддинг ловит смысл (имена+комментарии) лучше, чем синтаксис CREATE.
**29.** Что если таблица без COMMENT? — Карточка беднее, но имена колонок обычно несут смысл.
**30.** Где сериализуется? — JSON в `data/schema_catalog.json` (read-only в контейнере).

## Карточки таблиц (31–40)
**31.** Что такое карточка? — Текст ~5–15 строк: название, комментарий таблицы, список колонок (имя — комментарий).
**32.** Зачем не CREATE TABLE? — Синтаксис «фонит»; ключевые слова SQL сбивают эмбеддинги.
**33.** Пример карточки? — «credit_contract — Договоры кредитов\n· id — идентификатор\n· status — статус (1/2/3)\n· client_id — FK на клиента…»
**34.** Язык карточки? — Русский, как комментарии в DDL.
**35.** Сколько токенов в карточке? — 200–500 (зависит от ширины таблицы).
**36.** Включаем тип данных? — Опционально (date — намёк на временной фильтр).
**37.** Включаем FK? — Да, стрелка `client_id → clients(id)` — полезный сигнал для ранжирования.
**38.** Дёргаем sample-значения? — В проде да, на MVP — нет.
**39.** Когда перегенерируем? — При изменении схемы (ALTER); кэш в schema_catalog.json.
**40.** Что в логах? — Только имена; полный текст карточки — только в промпте.

## Эмбеддинги (41–50)
**41.** Какая модель? — multilingual-e5-large (или -base/-small под железо).
**42.** Размерность? — 1024 (large), 768 (base), 384 (small).
**43.** Размер модели? — large ~2.2 GB FP32 / ~1.1 GB FP16; small ~470 MB.
**44.** Где гоняем? — Прод — GPU; на 2 GB VPS — small или удалённый эндпоинт.
**45.** Префиксы «query: / passage: »? — Да, e5 требует. Карточка — passage, NL — query.
**46.** Нормализация? — L2 → косинус через внутреннее произведение.
**47.** Кэш эмбеддингов? — Да, pickle/JSON в `data/embeddings_cache`; ребилд по хешу.
**48.** Чем меряем близость? — Косинус (inner product нормализованных).
**49.** Метрика качества linking-а? — Recall@15 на размеченном датасете.
**50.** Целевой recall? — ≥0.9 на 60 таблиц.

## FAISS-индекс (51–60)
**51.** Зачем FAISS на 60? — Унификация API; на 60 — flat-index, точное сравнение.
**52.** Тип индекса? — IndexFlatIP. Для большого знания — IVF/HNSW.
**53.** Память FAISS? — 60 × 1024 × 4 байта ≈ 250 KB.
**54.** Скорость top-15? — Микросекунды.
**55.** Можно без FAISS? — Да, чистым numpy. FAISS — задел на масштаб.
**56.** Персистим индекс? — Ребилд в памяти при старте (быстро); на 1000+ — сохраняли бы.
**57.** NL-запрос короткий — recall падает? — Лечится reranker или BM25-hybrid.
**58.** Hybrid (BM25+dense)? — План; на MVP чистый dense.
**59.** Смешанный язык в запросе? — multilingual-e5 поддерживает 100+ языков.
**60.** Reranker (cross-encoder)? — В проде да, на MVP — нет.

## Schema linking + FK-замыкание (61–70)
**61.** Что делает linking? — На входе NL, на выходе подмножество таблиц для промпта.
**62.** Сколько top-K? — 15.
**63.** Почему 15? — Эмпирически: покрывает ~95% реальных JOIN-ов без раздувания промпта.
**64.** fk_closure после top-15? — Да: добавляем соседей по FK, чтобы JOIN не сломался.
**65.** Лимит после closure? — 20–25 таблиц.
**66.** Может ли не хватить? — Да; reflector добавит «нужна таблица X», следующая итерация её включит.
**67.** Что если генератор сослался на таблицу не из топ-15? — Аудитор/parser ловит → reject или clarifying-question.
**68.** Сохраняем выбор top-15? — В Langfuse-трейсе как metadata `schema_linking_tables`.
**69.** Можно фильтр по правам? — Да, top-K фильтруем до FAISS — но это L2/L3.
**70.** Если FAISS пустой? — Fallback на лексический grep + reflexion-предупреждение.

## Фронтенд (71–80)
**71.** Стек? — FastAPI + Jinja-шаблоны (SSR на MVP, минимум JS).
**72.** Какие страницы? — /, /audit-form, /audit-result, /admin (HTTP Basic).
**73.** SSE-стрим итераций? — Да, через `on_event` callback в pipeline.
**74.** Deep-link на Langfuse? — Да, `trace_id` пробрасывается в SystemResult.metadata.
**75.** Авторизация? — X-User header + HTTP Basic для /admin.
**76.** Где код фронта? — `src/case3/infra/service.py` + templates.
**77.** Что с CSP? — Langfuse iframe заблочен — даём внешнюю ссылку.
**78.** Что показываем при reject? — Все findings + recommendations + final risk + кнопка «уточнить запрос».
**79.** Локализация? — Русский UI (как комментарии в DDL).
**80.** Можно скачать audit_log? — Да, /admin отдаёт CSV/JSONL.

## Обновления и edge cases (81–90)
**81.** Эволюция схемы в проде? — Hooks на DDL-changes; пересчитываем затронутые карточки.
**82.** VIEW? — План: разворачиваем в исходные таблицы.
**83.** Materialized view? — Как обычная таблица для аудита.
**84.** PARTITIONED TABLE? — В каталоге — одна логическая таблица.
**85.** Сторонние схемы (public, audit)? — Поддерживаем namespace в Table.schema (default public).
**86.** Имена с UTF-8? — Поддержка через quote_ident; e5 справится.
**87.** Function-based индексы? — Не парсим (не нужно для генератора и аудитора).
**88.** Если DDL невалидный? — На pglast — exception, UI покажет «не удалось разобрать схему».
**89.** Изменения в комментариях — переэмбедить? — Да; дёшево (60 карточек).
**90.** Где тесты парсера? — `tests/test_schema_parser.py` (план, сейчас smoke).

## Альтернативы и обоснования (91–100)
**91.** Почему не sqlglot? — Подойдёт; pglast точнее на PG-специфике (PARTITION, PLPGSQL); за sqlglot Apache-лицензия — fallback.
**92.** Почему не graph-based linking? — Сложнее для MVP, задел в roadmap.
**93.** Почему не LLM-based linking? — Дорого; FAISS даёт почти 100% recall@15 дешевле.
**94.** Почему e5, а не SBERT? — e5 топ на MTEB retrieval, multilingual из коробки.
**95.** Можно ли pgvector в Postgres? — Да, опц. в проде. На MVP — FAISS.
**96.** Чем меряли качество карточек? — Recall@15 на 14 seed-запросах; цель ≥0.9.
**97.** Если карточка слишком длинная? — Обрезаем по токенам (e5 max 512 для passage).
**98.** Кэш индекса по хешу DDL? — Да, ребилд только при изменении.
**99.** Что в индексе кроме карточек? — На MVP — нет; в проде — sample значений, статистика колонок.
**100.** Что демонстрирует Уч.1? — Фронт `localhost:18000`: ввод NL → выделение релевантных таблиц (top-15) + видна fk-замыкание; админка с экспортом аудит-лога.
