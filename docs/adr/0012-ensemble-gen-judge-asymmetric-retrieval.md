# ADR-0012 — Ансамбль генератора и судьи: bagging/boosting + асимметричный retrieval

- **Status:** Proposed
- **Date:** 2026-05-23
- **Deciders:** project owner
- **Refines:** ADR-0002 (цикл), ADR-0004 (гибридный аудитор), ADR-0005 (RAG),
  ADR-0006 (датасет). Не отменяет их — добавляет слой ансамблирования.

## Context

Возникли два связанных вопроса по архитектуре цикла «генератор ↔ судья»:

1. Можно ли отдать **одну модель** под обе роли (экономия ресурсов: кейс —
   on-prem, ≤30B параметров, ограниченные ресурсы, ctx 100–256k, см.
   `case_3.txt`)?
2. Что если пойти в **мультиагента с ансамблем** (bagging/boosting нескольких
   моделей) и сделать **асимметричный retrieval**: судья тянет примеры
   «как НЕ надо» (уязвимые), генератор — «как надо» (безопасные/эталонные)?

Ключевой враг ансамбля судьи — **скоррелированные ошибки**: одна модель,
породившая уязвимый SQL, его же и не заметит при самооценке. Поэтому
независимость участников и асимметрия знаний — не украшение, а суть.

**Что изменилось и делает идею реализуемой сейчас.** По ADR-0006 датасет
эволюционировал: `dataset/generate_dataset.py` собирает **500 записей на
реальной схеме** (300 safe + 200 уязвимых по 10 классам), у каждой уязвимой
пары есть `sql_bad` + парный `sql_good` (один `seed_id`), поля `vuln_class`,
`is_vulnerable`, `tables`, `split`. Это одновременно:

- **источник few-shot** для обеих ролей (good → генератору, bad → судье);
- **eval-харнесс** (recall судьи на 200 bad, FP на 200 good-двойниках, EX
  генератора на safe-эталонах).

Текущая база (что переиспользуем):

- ADR-0004: судья уже **гибридный** — Phase 1 детерминированный (pglast
  R001-R013 + EXPLAIN + sensitive-regex) ловит структурные классы, Phase 2
  LLM — триаж. Реальная ловля — на Phase 1.
- ADR-0005: RAG-знания (CWE/CAPEC/OWASP/PG-docs) для судьи. **Важно:**
  payloads/`kb.payloads` явно запрещены в runtime-контексте судьи («иначе
  модель начнёт учиться и предлагать опасный SQL») — это ограничение нужно
  согласовать с асимметричным retrieval (см. Decision §1).
- ADR-0003: генератор — prompt-engineering без fine-tuning.

Опоры в обзоре (`research/`):

- **QLPro** (`research/01`, §«periphery») — *triple-voting LLM-judges поверх
  static analysis*. Прямой прецедент: ансамбль-голосование судей **над**
  детерминированным слоем.
- **DAIL-SQL** (`research/01`, блок 1) — 5 представлений вопроса +
  **execution-based self-consistency voting**. Опора для bagging генератора.
- **Reflexion / Self-Refine** (`research/01`, блок 2) — «вербальный RL»,
  память об ошибках. Опора для hard-example mining и узла reflector.
- **MAC-SQL Refiner** (`research/00`, `research/01`) — цикл с правкой по
  security-feedback.

## Decision (предложение)

### 1. Асимметричный retrieval — ядро

Из train-сплита датасета строим **два непересекающихся** few-shot-индекса:

```
dataset (split=train)
   ├── is_vulnerable=False  ──►  idx.positives   →  ТОЛЬКО генератор  («как надо»)
   └── is_vulnerable=True   ──►  idx.negatives   →  ТОЛЬКО судья     («на что ловить»)
        + vuln_class, note                          (+ RAG-знания ADR-0005)
```

- Маппинг полей: `is_vulnerable` → индекс; `vuln_class` → фильтр запроса
  судьи; `tables`/`nl` → schema-aware similarity (e5 + FAISS, как в ADR-0003).
- **Согласование с ADR-0005 (запрет payloads в контексте судьи).** Запрет был
  про то, чтобы модель **не научилась генерировать** опасный SQL. Здесь
  `idx.negatives` уходит **только в детектирующий контекст судьи** и **никогда**
  в контекст, который видит генератор. Это самостоятельный аргумент держать
  роли как **раздельные промпт-контексты** (а лучше — раздельные сэмплинги),
  чтобы позитивный и негативный сторы не смешивались. Если веса всё же общие
  (экономия) — изоляция контекстов обязательна.
- **Анти-leakage:** индексы строим строго из `split=="train"`, метрики меряем
  на `split=="eval"`. Поля уже есть в датасете.

### 2. Генератор — bagging (снижение variance): best-of-K

```
intent + schema
   │  retrieve top-k из idx.positives
   ▼
┌───────────────── K кандидатов (разнообразие) ─────────────────┐
│  temperature × prompt-representation (DAIL-SQL 5 видов) × seed │
│  [опц. 2-е семейство модели ≤30B для де-корреляции]            │
└───────────────────────────┬───────────────────────────────────┘
                            ▼  re-rank
   риск судьи (↓)  +  EX-proxy (EXPLAIN парсится, форма результата)
                    +  self-consistency-кластеры (DAIL-SQL voting)
                            ▼
                 min-risk кандидат, удовлетворяющий интенту
```

Bagging здесь честный: параллельные независимые сэмплы + агрегатор.

### 3. Судья — boosting-style каскад (снижение bias) + голосование (QLPro)

```
sql_candidate
   ▼
[Stage 0] Phase 1 детерминированный (ADR-0004)        ← независим по построению, «бесплатен»
   │  структурные классы (DML_NO_WHERE, SELECT_STAR, инъекции по AST) → ~max recall
   ▼  остаточные/неоднозначные случаи
[Stage 1] скамья из N LLM-судей (голосование, QLPro)  ← разнообразие prompt/temp/[модель]
   │  каждый: idx.negatives (few-shot «на что ловить») + RAG-знания (ADR-0005)
   │  специализация на ОСТАТОЧНЫХ трудных классах:
   │     PRIV_ESCALATE, PLPGSQL_UNSAFE, SQL_INJ_TIME, тонкий DIRECT_SENSITIVE
   ▼  [опц. Stage 2] тай-брейк только при несогласии голосов
агрегация рисков по классам → сумма vs RISK_THRESHOLD=4.0
```

- **Агрегация под вашу метрику** (сумма risk_score по классам < 4.0): для
  каждого `vuln_class` объединяем риск участников — взвешенный голос / `max`
  для recall-критичных классов, **калиброванно**, чтобы не разносить FP на
  good-двойниках. Сумма по классам → approve/reject.

### 4. Bagging vs boosting — честное различие

| | Bagging | Boosting |
|---|---|---|
| Как | параллельно, независимо, голос/среднее | последовательно, каждый чинит ошибки предыдущего |
| Снижает | **variance** | **bias** |
| Где у нас | генератор (K кандидатов), скамья судей (Stage 1 голоса) | каскад судьи (Stage 0→1→2) |
| Честность | настоящий bagging | **НЕ** AdaBoost/GBM |

С **замороженными** LLM настоящего boosting (переобучение с перевзвешиванием)
нет. Реализуем «boosting по духу» = **каскад специалистов**: следующая стадия
получает в `idx.negatives` именно те примеры, на которых ошиблась предыдущая
(hard-example mining, §5), + переранжирование retrieval в пользу трудных
негативов. Это надо проговаривать прямо, чтобы не переобещать.

### 5. Hard-example mining — «топливо» каскада + связь с reflector

```
прогон ансамбля на train
   ├── FN (bad прошёл как safe)  → добавить/поднять вес в idx.negatives стадии N+1
   └── FP (good помечен)         → «trick-safe» якоря для калибровки порога
                                    reflector (Reflexion, Qwen-7B) → Lessons → state генератора
```

Замыкает уже существующий цикл reflector из ADR-0002.

### 6. Согласование с ресурсами (≤30B, on-prem)

Ансамбль дороже. Митигации по приоритету:

- генератор: **implicit ensemble** — одна модель, K сэмплов (дешёвое
  разнообразие) **до** добавления 2-го семейства;
- судья: каскад гасит большинство кейсов на Stage 0 (бесплатно); LLM-голоса
  только на неоднозначных/трудных классах; N ограничен (≈3, как QLPro);
- квантизация (AWQ/GPTQ) под совмещение ролей на одной GPU; при нехватке VRAM
  — последовательное мультиплексирование роли на одних весах;
- лимит итераций цикла (ADR-0002) ограничивает суммарные K и стадии.

### 7. Оценка (на датасете 500; A/B — плюс к ВКР)

- **Судья:** recall по каждому классу на 200 bad + FP-rate на 200 good-двойниках;
  итог — сумма рисков vs порог.
- **Генератор:** EX на safe-эталонах (ADR-0007); доля «approved без остаточной
  уязвимости».
- **Абляции:** одиночный vs bagged генератор; одиночный судья vs голосование;
  **симметричный vs асимметричный** retrieval; с/без hard-example mining.
- Жёстко: индексы из `split=train`, метрики на `split=eval`.

## Consequences

**Положительные**

- Выше recall судьи (голосование + независимый Stage 0) и выше EX генератора
  (best-of-K) — две основные метрики кейса.
- Асимметричный retrieval — чистый дешёвый рычаг, **напрямую питается нашим
  датасетом** (good/bad уже размечены и спарены).
- Hard-example loop переиспользует reflector — без нового компонента.
- Готовая A/B-история (ансамбль vs одиночка, симметрия vs асимметрия) — бонус ВКР.

**Отрицательные / Риски**

- **Корреляция участников** → ансамбль почти не даёт выигрыша. Разнообразие —
  всё. Потолок ≤30B ограничивает разнообразие семейств → опираемся на
  prompt/temperature/seed и на независимый Stage 0.
- **Рост FP** от recall-жадной агрегации (срабатывания на good-двойниках) →
  нужна калибровка порога.
- **Латентность/компьют** умножаются на K и на число судей.
- **RAG-leakage**, если train/eval не разнесены.
- **Payload-in-context**, если контексты генератора и судьи смешать (см. §1).
- «Boosting» здесь — каскад специалистов, **не** настоящий boosting.

## Alternatives considered

| Альтернатива | Почему не основная |
|---|---|
| Одна модель, две роли промптами, один проход | Дешевле всего, но self-bias. Оставляем как **baseline A** в A/B. |
| Одиночный LLM-судья над Phase 1 (текущий ADR-0004) | База; ансамбль должен побить его в абляции. |
| Симметричный retrieval (общий стор для обеих ролей) | Проще, но теряет сигнал good/bad. Абляция покажет цену асимметрии. |
| Настоящий boosting через дообучение мелкого детектора на остатках (LoRA 7B) | Возможно позже; ADR-0003 зафиксировал «без fine-tuning» для MVP. |
| Чистый bagging-судья без детерминированного Stage 0 | Теряем дешёвую высокорекольную структурную сетку; дороже и хуже. |
| N×32B bagging в лоб | Не лезет в on-prem-бюджет; начинаем с implicit ensemble. |
