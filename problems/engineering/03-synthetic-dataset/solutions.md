# Варианты решения: Синтез датасета

## Альтернативные подходы

| # | Подход | Плюсы | Минусы | Решение |
|---|---|---|---|---|
| A | Полностью ручная разметка 300 пар (NL→SQL) | Качество максимально | 30-50 ч работы; нет масштабирования | ❌ |
| B | Брать BIRD / Spider / KaggleDBQA как train | Уже размечено | На других схемах; не учит модель домену GreenData | ❌ как main |
| C | Чистый Text-to-SQL: писать NL, просить LLM генерировать SQL | Привычный flow | Качество синтезированного SQL ниже; обязательная валидация на исполнение | ❌ |
| D | **SQL-to-Text back-translation (OmniSQL стиль)** | Качество NL у LLM выше; SQL-seed контролируем сами | Нужен seed pool из 300 SQL — это всё равно 10 ч ручной работы | ✅ выбрали |
| E | Полный OmniSQL-pipeline (2.5M примеров с автогенерацией БД) | SOTA по объёму и разнообразию | Безумно дорого для MVP; домен будет случайный, не GreenData | вне MVP |
| F | SING-SQL: complexity-controlled с LLM-judge валидацией | Контроль сложности; качество | Дорого по latency, нужна полная пайплайн-инфраструктура | для v2 |
| G | Закупить разметку (Толока, Scale AI) | Качество, объём | Платно, NDA-вопросы, медленнее | вне формата хакатона |

## Объёмы и состав (что выбрали)

| Класс | Кол-во | Источник SQL |
|---|---|---|
| Безопасные / эталонные | 200 | Ручная разработка по `data_model_sql/data_model.sql` |
| `SELECT_STAR` | 10 | Ручные |
| `DML_NO_WHERE` | 10 | Ручные |
| `NO_PAGINATION` | 10 | Ручные |
| `DIRECT_SENSITIVE` | 15 | Ручные |
| `SQL_INJ_CLASSIC` | 15 | Адаптации PortSwigger PG + sqlmap |
| `SQL_INJ_UNION` | 10 | sqlmap `union_query.xml` |
| `SQL_INJ_TIME` | 10 | `pg_sleep` payloads |
| `PRIV_ESCALATE` | 10 | PG docs примеры |
| `PLPGSQL_UNSAFE` | 10 | `EXECUTE format/\|\|` антипаттерны |
| **Итого** | **300 SQL** | **+10 баллов за датасет с уязвимостями (≥ 50)** |

На каждый SQL — **2 NL-варианта** (short + long) → 600 пар.

## Что выбрали и почему

**D (SQL-to-Text back-translation)** на собственной схеме.

Аргументы:
- **Менторская рекомендация прямая**: «SQL-to-Text проще, чем Text-to-SQL. Минимум 300 примеров».
- **Доменная релевантность**: SQL пишется по `data_model.sql` GreenData, не по чужим схемам.
- **Качество NL**: LLM генерирует естественный русский лучше, чем синтезирует валидный SQL.
- **Контроль уязвимостей**: уязвимые SQL формируем сами адаптацией PortSwigger/sqlmap — никаких сюрпризов.
- **Стоимость**: 600 NL × ~2K токенов = ~$0.20 через GPT-4o-mini. Бесплатно.

Полный OmniSQL-pipeline (E) даст 2.5M примеров, но домен будет рандомный — нам не нужен.

## Реализация (ADR-0006)

### Пайплайн

```
Step A: SQL seed pool (300 SQL — ручные + адаптации PortSwigger/sqlmap)
   │
   ▼
Step B: SQL-to-Text (Qwen-Coder 32B / GPT-4o-mini)
   - объясни SQL пошагово
   - сформулируй 2 NL-вопроса (short + long)
   - оцени сложность easy/med/hard
   - если уязвим — укажи vuln_class
   - JSON-output
   │
   ▼
Step C: Validation
   - pglast.parse_sql() — синтаксически валиден
   - для SELECT — исполнить в sandbox без ошибки
   - NL содержит упоминание ключевых таблиц/колонок (LLM-judge sanity check)
   │
   ▼
Step D: Human review
   - спот-чек 20% выборки одним человеком (~2 часа)
```

### Промпт SQL-to-Text

```
Дана PostgreSQL-схема: {ddl_chunk}
Дан SQL-запрос: {sql}

1. Опиши пошагово, что делает запрос (3-5 предложений).
2. Сформулируй 2 разные NL-формулировки задачи для аналитика
   (короткая + развёрнутая «зачем»).
3. Оцени сложность: easy/medium/hard.
4. Если SQL уязвим — какой класс из списка [SELECT_STAR, ...].

Верни JSON: {step_by_step, nl_short, nl_long, difficulty, vuln_class}.
```

### Train / Eval split
- `train`: 240 SQL (= 80%), 480 NL-вариантов.
- `eval`: 60 SQL (= 20%), 120 NL-вариантов.
- Стратификация по `vuln_class` и `difficulty`.
- Seed=42, версионируется в `data/splits/v1.json`.

### Quality gate перед merge
1. 100% примеров парсятся `pglast` без ошибок.
2. 100% безопасных SELECT исполняются в sandbox.
3. 100% примеров с `vuln_class != "safe"` детектируются хотя бы одним Phase 1 правилом (ADR-0004) — sanity check.

## Что измеряем

| Метрика | Цель |
|---|---|
| Размер eval | ≥ 100 NL-пар |
| Стратификация по difficulty | ≥ 20% каждой группы |
| Class balance (vuln vs safe) | ~33% / 67% |
| Recall@iterAny по каждому `vuln_class` | ≥ 0.80 |
| Inter-rater agreement по 20% спот-чека | ≥ 0.85 |
| Стоимость синтеза | < $5 |

## Что может пойти не так

| Проблема | Митигация |
|---|---|
| Faker-данные не покрывают распределение → `gold_sql` возвращает 0 строк → ложный EX=1 | При сидинге проверяем `len(gold_result) > 0`; иначе меняем seed |
| LLM генерирует слишком «гладкий» русский, все NL похожи | 2 формулировки на SQL + 20% human review с инструкцией «парафразируй разговорно» |
| Дрейф domain knowledge (схема может измениться) | Версионирование `v1.json` |
| Утечка train→eval через похожие формулировки | При сплите cosine между train и eval, отсекаем cosine > 0.9 |
| LLM ошибся в `vuln_class` метке | Quality-gate «Phase 1 должен подтвердить класс»; иначе в ручной review |
