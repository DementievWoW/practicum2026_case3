# 04 — Ненадёжность LLM-as-judge

## Что

«Просто попросить LLM оценить SQL на безопасность» **не работает надёжно**. LLM-судья даёт:
- **False Positives** — помечает безопасный запрос как уязвимый («это может быть инъекцией, если ...»).
- **False Negatives** — пропускает реальные SQLi-payloads после обфускации.
- **Inconsistency** — на одном и том же SQL даёт разные `risk_score` между прогонами.
- **Hallucinations** — придумывает несуществующие CWE/CAPEC-ID.

Это бьёт прямо в **25 баллов** критерия «Покрытие классов уязвимостей: судья выявляет не менее 5 классов, по каждому формирует объяснение и оценку риска» (`tusk`).

## Почему критично

Если судья ненадёжен — все наши 9 классов уязвимостей превращаются в случайные оценки. На защите эксперт-оценщик легко покажет два SQL: один безопасный (FP — судья отклоняет), второй с явной SQLi через простую обфускацию (FN — судья одобряет).

Подкреплено материалами:
- **IEEE 2025 «SQL Injection in LLM-Generated Queries»**: **100% evasion rate** для SQLFluff/SQLLint/SonarQube по adversarial-payloads. То есть **один любой статический инструмент не справляется**.
- **Trend Micro «LLM as a Judge»**: LLM работает надёжно, **только когда вся улика в промпте**. Если LLM сама должна «догадаться» по контексту — провал.
- **ToxicSQL (SIGMOD 2025)**: 0.44% отравленных данных в training → 79.41% backdoor-success rate. LLM-судья даже потенциально уязвим к backdoor.
- **Ментор `take1`**: «LLM-as-judge для оценки качества SQL сомнителен».

## Силы, тянущие в разные стороны

| Куда тянет | Аргумент |
|---|---|
| **Только LLM-judge** | Просто, гибко, понимает контекст |
| **Только статика** | Детерминированно, аудируемо, быстро |
| **Гибрид** | Дороже в инженерии, но обходит обе крайности |
| **Жёсткий промпт «найди ВСЕ уязвимости»** | Меньше FN |
| **Промпт «отнесись скептически»** | Меньше FP |
| **Один LLM-вызов** | Дёшево |
| **Multi-judge consensus** | Дороже, но устойчивее |

## Наше решение (ADR-0004)

**Не «LLM-as-judge», а «LLM-as-triager».** Двухфазный пайплайн:

### Phase 1 — детерминированный слой (pglast Visitor + EXPLAIN)
- 11 правил из ADR-0004 (`R001`...`R011`), плюс 6 PL/pgSQL правил из ADR-0010.
- Каждое правило возвращает `Finding(rule_id, vuln_class, severity, risk_score, location, snippet, evidence_refs)`.
- Это **обязательный нижний слой**: даже если LLM упадёт, мы что-то покажем.

### Phase 2 — LLM-судья **поверх findings**
LLM **не делает обнаружение с нуля**, а:
1. **Триажирует findings** — подтверждает или помечает как FP.
2. **Выставляет финальный `risk_score`** на каждый подтверждённый finding.
3. **Формирует `description` + `recommendation`** на естественном языке.
4. **Ищет дополнительные уязвимости**, которые правила в принципе не могут поймать (логика, контекст).

### RAG в Phase 2 (ADR-0005)
LLM получает top-5 чанков из `kb.cwe` ∪ `kb.capec` ∪ `kb.owasp` по `vuln_class`. Это даёт:
- **Верифицируемые ссылки** в `evidence.cwe_id`, `evidence.capec_id`.
- **Снижение галлюцинаций** ID — judge не может выдумать CWE-9999, потому что в его RAG-контексте только реальные ID.

### Антигаллюцинационный валидатор (ADR-0005 §7)
После ответа judge регексом `CWE-\d+` / `CAPEC-\d+` извлекаем ID, проверяем их наличие в `kb.cwe` / `kb.capec`. Если нет — заменяем `evidence` на пустое + флаг `metadata.unverified = true`.

### Structured output
`response_format = {"type": "json_object"}` (OpenAI-совместимый mode у DeepInfra/OpenRouter) → judge обязан вернуть валидный JSON. Fallback — Pydantic-валидатор + retry × 2.

### `risk_score` через MAX, не SUM
ADR-0004 §6: `overall_risk_score = max(v.risk_score for v in vulnerabilities)`. SUM теоретически указан в ТЗ как «метрика безопасности», но в практике мелкие info-findings (3 × 1 = 3) суммировались бы выше критического (одного × 8). Документируем выбор; переключение на SUM — одна строка кода.

## Trade-off

**Дороже в инженерии:** надо писать 11+ правил pglast, держать sandbox-БД для EXPLAIN, валидировать JSON, верифицировать CWE-ID. Но без этого критерий 25 баллов уязвим.

**Latency-стоимость:** Phase 1 быстрая (~50ms на правило), но LLM-judge добавляет ~3-5 сек. Укладываемся в общий бюджет 40 сек (см. [05-latency-budget](../05-latency-budget/)).

## Что измеряем

| Метрика | Цель | Источник истины |
|---|---|---|
| **Recall судьи** по каждому `vuln_class` | ≥ 0.80 на iter1, ≥ 0.90 на iterAny | eval-set с разметкой ADR-0006 |
| **Precision судьи** (нет FP на безопасных) | ≥ 0.85 | eval-set, безопасная часть |
| **Кол-во unverified evidence** | ≤ 5% | Антигаллюцинационный валидатор |
| **Consistency**: 3 прогона на тот же SQL дают одинаковый `vuln_class` | ≥ 0.95 | Отдельный test-run |
| **Recall на adversarial payloads** (sqlmap, PortSwigger) | ≥ 0.70 | `kb.payloads` regression set |

## Что может пойти не так

1. **Adversarial payloads из `kb.payloads`** обходят Phase 1 (правила слишком прямолинейны). Phase 2 их тоже не ловит, потому что в её RAG-контексте только описания CWE, не payloads. Митигация: документируем как известное ограничение, на защите упоминаем GSQLi/RobustJudge как направление будущей работы.
2. **LLM возвращает JSON, который не парсится** — retry × 2, но если третий раз тоже invalid, возвращаем findings-only без LLM-объяснений (degraded mode).
3. **RAG не подтянул релевантный чанк** (cosine miss) — judge даёт `evidence: {}` + `unverified: true`. На UI помечаем «без верифицируемой ссылки на стандарт».
4. **Backdoor-атаки на LLM** (ToxicSQL) — для open-source модели от провайдера риск низкий; но если провайдер скомпрометирован — мы беззащитны. Митигация: regression-тесты на стабильных payloads каждый билд.
