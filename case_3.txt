Кейс GreenData посвящён разработке мультиагентной связки «Генератор SQL + Судья» для low‑code платформы, работающей поверх PostgreSQL в банковских и корпоративных системах. В рамках проекта аналитики и LLM‑агенты создают SQL‑запросы по текстовым описаниям, но без аудита возникают риски SQL‑инъекций, деструктивных операций типа DROP, тяжёлых запросов и утечек PII. Требуется реализовать пайплайн, в котором генератор по текстовому промпту и схеме базы данных формирует SQL, а судья (аудитор) оценивает безопасность запроса, возвращает оценку и исправленную версию, после чего цикл повторяется до одобрения или исчерпания итераций. Необходимо вести логи аудита с эволюцией запросов и категоризировать ошибки по типам уязвимостей. Метрика безопасности рассчитывается как сумма риск‑скоров, которая должна быть ниже порога. Исполнение SQL на проде не требуется — конечными артефактами являются сгенерированный запрос и его оценка, интеграция с выполнением остаётся на стороне платформы. Разрешено использование облачных LLM‑API, но целевая архитектура рассчитана на модели до 30 миллиардов параметров (например, Qwen‑Coder 32B или специализированные code‑модели), поскольку заказчик разворачивает систему в своём контуре с ограниченными ресурсами. Контекстное окно моделей ограничено 100–256 тысячами токенов. Для валидации запросов применяются инструменты: EXPLAIN для оценки тяжести и проверки исполнимости без данных, sandbox‑окружение с миграциями, база знаний по SQL‑инъекциям (MITRE SQL Attack) в виде RAG для судьи, а также тулы для чтения схемы и первых строк таблиц, необходимые генератору. Архитектура подразумевает мультиагентность внутри одного LLM‑контура с общим workflow и циклом «генератор‑судья», без разнесения по микросервисам. Метрики включают точность генерации (по эталонным SQL) и покрытие уязвимостей (по размеченным вредоносным примерам). Стек разработки: Python, предпочтительно Jupyter Notebook, основная СУБД — PostgreSQL, поддержка других СУБД приветствуется, хранение в Git. Ментор указывает на подводные камни: без подачи DDL и семплов LLM генерирует плохой SQL, поэтому обязателен соответствующий тул; валидационного датасета «промпт → SQL → эталон», скорее всего, не дадут, и его придётся синтезировать самостоятельно (это даёт дополнительные баллы); LLM‑as‑judge для оценки качества SQL сомнителен, лучше сравнивать результаты выполнения запросов на эталонных данных; AB‑тесты считаются экзотикой для хакатона, но их наличие будет плюсом к выпускной квалификационной работе. Кейс ориентирован на команды, интересующиеся агентными архитектурами, промпт‑инжинирингом, LLM‑инжинирингом, RAG, tool calling и workflow‑фреймворками (LangGraph, LlamaIndex), с пониманием SQL и информационной безопасности баз данных. Распределение ролей: подготовка данных (один человек), разработка инструментов (один), LLM‑инженер (один), аналитик (один). При успешном решении возможна интеграция в платформу GreenData, стажировка или трудоустройство, а также получение востребованного опыта работы с агентами. По сравнению с другими кейсами этот — самый инженерный, с минимумом DS‑математики и упором на архитектурный дизайн агентов; если требуется именно машинное обучение, данный кейс не подходит.
