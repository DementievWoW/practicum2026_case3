# Круг 6 — Ансамбль генератора/судьи + асимметричный retrieval

> Целевой круг под [ADR-0012](../docs/adr/0012-ensemble-gen-judge-asymmetric-retrieval.md).
> Вопрос: стоит ли делать мультиагента с bagging/boosting нескольких моделей
> для генератора и судьи, и давать им **асимметричный** few-shot (судье —
> «как НЕ надо» / уязвимые, генератору — «как надо» / безопасные).
> Здесь — внешние прецеденты (пейперы) и как они ложатся на наш дизайн.
> Внутренние материалы (`research/01–05`) ревьюит вторая половина команды.
> Верифицированные карточки по этому кругу (отдельно от «старого» ресёрча) —
> в [`research/materials_round6/`](materials_round6/).

## Блок 1. Ансамбль / жюри LLM-судей (bagging судьи)

### 1.1 PoLL — Replacing Judges with Juries (arXiv 2404.18796) ⭐
- **Панель из нескольких МЕЛКИХ моделей разных семейств** (Command R + GPT-3.5
  + Haiku) бьёт одного крупного судью, **дешевле в 7×**, и **меньше intra-model
  bias** (за счёт непересекающихся семейств). Агрегация — max/avg voting.
- → Прямая опора для нашей «скамьи судей» Stage 1. Главное: выигрыш даёт
  **разнообразие семейств**, а не размер.

### 1.2 More Agents Is All You Need / Agent Forest (arXiv 2402.05120)
- Просто **sampling-and-voting**: гоним вход N раз, majority vote. Качество
  растёт с числом агентов; 20×Llama2-13B ≈ Llama2-70B.
- **Порог сложности:** после некоторого N прироста нет. → N держим небольшим
  (≈3–5), не раздуваем.

### 1.3 Reliability of LLM-as-a-Judge (arXiv 2412.12509) + Survey (2411.15594)
- Майорити-voting **повышает надёжность**, но **не лечит систематические
  (скоррелированные) смещения**. Экспертиза судьи **контекст-зависима**.
- **minority-veto** (несколько «вето» → метка invalid) заметно поднимает TNR.
- → Подтверждает наш главный риск: корреляция участников. Для recall-критичной
  задачи полезен вариант агрегации «любой уверенный голос → флаг» (veto в
  обратную сторону), но он же раздувает FP → нужна калибровка на good-двойниках.

### 1.4 QLPro (arXiv 2506.23644) ⭐ — уже в `research/01`
- **Triple-voting**: каждый API оценивается LLM в 3 разных контекстах,
  итог — majority. Поверх **статанализа** (CodeQL-правила). 66.1% vs 38.7% у
  голого CodeQL, нашли 6 0-day.
- → Канон нашей схемы: голосующие LLM-судьи **над** детерминированным слоем
  (наш Phase 1). Тройное голосование одной моделью в разных контекстах —
  дешёвый способ де-коррелировать без второго семейства.

## Блок 2. Diversity vs Quality — критично для ≤30B

### 2.1 Self-MoA / Rethinking Mixture-of-Agents (arXiv 2502.00674) ⭐⭐
- Смешивание **разных** LLM часто **СНИЖАЕТ** среднее качество. **Self-MoA**
  (ансамбль сэмплов одной лучшей модели) бьёт классический MoA: +6.6% на
  AlpacaEval 2.0, +3.8% в среднем. Есть и `Self-MoA-Seq` (последовательная
  агрегация на лету).
- → **Сильнейший аргумент** под наш бюджет: вместо того чтобы подмешивать
  слабые модели ≤30B, лучше брать ОДНУ сильную (Qwen-Coder) и гонять **K
  сэмплов** (implicit ensemble). Совпадает с митигацией §6 ADR-0012.
- ⚠️ Корректирует тезис «разнообразие семейств — всё» (PoLL): разнообразие
  помогает только если не топит качество. Для нас — разнообразие через
  prompt/temperature/контекст (как QLPro), а не через слабые модели.

### 2.2 Mixture-of-Agents (arXiv 2406.04692)
- Слоистая агрегация: каждый слой видит выходы предыдущего. Только open-source
  LLM дают 65.1% на AlpacaEval (> GPT-4o 57.5%). Феномен «collaborativeness».
- → Опция «агрегатор-судья поверх голосов» (наш Stage 2 тай-брейк), но дорого;
  для MVP избыточно (см. Self-MoA как более дешёвую альтернативу).

## Блок 3. Генератор: генерация кандидатов + выбор (bagging генератора)

### 3.1 CHASE-SQL (ICLR 2025, arXiv 2410.01943) ⭐
- 4 компонента: value retrieval → **candidate generator** (divide-and-conquer +
  CoT по плану выполнения + instance-aware few-shot) → **query fixer** (цикл
  правок) → **selection agent** (обученный **бинарный** селектор, попарное
  сравнение). 76.02% на BIRD.
- Ключевое: **обученный селектор > обычного consistency-voting**.
- → Наш best-of-K = упрощённая CHASE-SQL. Селектор у нас пока **не обучаем**
  (ADR-0003: без fine-tuning) → используем self-consistency + риск-судьи как
  ранкер. CHASE-SQL-селектор — апгрейд-путь, если разрешим LoRA.

### 3.2 CSC-SQL — Corrective Self-Consistency (Semantic Scholar)
- Self-consistency + RL-коррекция кандидатов. → идея: не просто голосовать, а
  **чинить** меньшинство (перекликается с нашим query-fixer/reflector).

### 3.3 DAIL-SQL (в `research/01`) + Agent Forest (1.2)
- Execution-based **self-consistency voting**, 5 представлений вопроса. → база
  нашего bagging генератора без обучения.

## Блок 4. Асимметричный / знаниевый RAG для ДЕТЕКЦИИ (ядро идеи) ⭐⭐

### 4.1 Vul-RAG (arXiv 2406.11147) ⭐⭐ — почти 1:1 наша идея
- Голые LLM различают **уязвимый vs пропатченный** код с точностью всего
  **0.06–0.14** (!). Vul-RAG строит **knowledge-level** базу из исторических
  пар «уязвимость + фикс»: извлекает **причину, функциональную семантику,
  способ исправления**, и подтягивает это в контекст судьи.
- Итог: **+16–24%** accuracy на различении vuln/patched; ручная детекция
  60%→77%; нашли 10 багов в ядре Linux (6 CVE).
- → **Прямое обоснование** нашего `idx.negatives`. И killer-факт: различать
  `sql_bad` vs парный `sql_good` голой моделью **очень трудно** — значит
  негативный знаниевый стор не «приятный бонус», а необходимость. Наш датасет
  (спаренные good/bad + `vuln_class` + note) — ровно такой источник знаний.

### 4.2 SQLi-детекторы: RAG + Self-Ranking (arXiv 2411.18216)
- RAG поверх few-shot даёт до **+66 п.п. F2** (в среднем +17), Self-Ranking
  ещё до +43 п.п. на детекции SQLi.
- → Подтверждает связку «RAG-знания (ADR-0005) + ранжирование» для судьи.

### 4.3 Трудность выбора few-shot для детекции уязвимостей (arXiv 2510.27675)
- Две стратегии: (а) брать примеры, на которых модель **стабильно ошибается**
  (= hard-example mining!), (б) kNN по семантике. Для Python/JS помогает, для
  C/C++ — почти нет.
- → Поддерживает наш hard-example loop, но с оговоркой: эффект **доменно-
  зависим**; обязательно мерить на нашем eval, не верить переносу.

### 4.4 MulVul (arXiv 2601.18847)
- Retrieval-augmented **мультиагентная** детекция уязвимостей + cross-model
  prompt evolution. → созвучно нашей связке «мультиагент + RAG + эволюция
  промптов через reflector».

### 4.5 SqliGPT (MDPI applsci 14/16/6929), «SQLi in LLM-Generated Queries»
- LLM для black-box детекции SQLi; систематический разбор того, что
  **LLM-сгенерированный SQL** регулярно содержит инъекции и детекторы их
  пропускают. → ровно наша постановка (генератор может выдать уязвимый SQL).

## Блок 5. Boosting БЕЗ дообучения (уточняет «boosting≠boosting» из ADR)

### 5.1 PromptBoosting (arXiv 2212.09257) ⭐
- **AdaBoost поверх промпт-weak-learners**: weak learner = промпт × элемент
  выходного распределения; ансамблируются классическим AdaBoost. Только
  forward-проходы, **без backward**.
- → Значит «boosting по духу» в ADR-0012 можно усилить: есть **легитимный**
  способ настоящего boosting на **замороженных** весах. Кандидат для каскада
  судьи на трудных классах.

### 5.2 Language Models are Weak Learners (arXiv 2306.14101)
- LLM-«саммари» как weak learners в boosting, **без retrain**, только промпт.

### 5.3 PREFER (arXiv 2308.12033)
- Prompt ensemble через Feedback-Reflect-Refine + «prompt bagging». → прямой
  мост к нашему reflector (Reflexion) как генератору новых промптов-учеников.

## Как это меняет ADR-0012 (предлагаемые правки)

1. **Разнообразие.** Заменить «разнообразие семейств — всё» на: при ≤30B —
   **Self-MoA** (K сэмплов одной сильной модели) + декорреляция через
   prompt/temperature/контекст (QLPro triple-voting). Подмешивать слабые
   семейства — только если абляция покажет, что не топят качество (2502.00674).
2. **Boosting.** Смягчить «настоящего boosting нет»: есть **PromptBoosting /
   LMs-as-weak-learners** — AdaBoost на замороженных весах через промпты.
   Каскад специалистов остаётся, но как один из вариантов, а не единственный.
3. **Негативный стор — не опция, а необходимость.** Добавить факт Vul-RAG
   (0.06–0.14 у голой LLM на vuln/patched) как обоснование `idx.negatives` и
   того, что различать наши good/bad-двойники трудно без знаний.
4. **Агрегация.** Учесть minority-veto (2412.12509) как recall-режим + явную
   калибровку порога на 200 good-двойниках (контроль FP).
5. **Селектор генератора.** Зафиксировать CHASE-SQL-селектор как апгрейд-путь
   (если снимем «без fine-tuning»), сейчас — self-consistency + риск-ранкер.

## Гэпы / чего не нашли (открытые вопросы)

- **Прямого прецедента «асимметричный few-shot: позитивы генератору vs
  негативы судье в ОДНОМ цикле gen↔judge»** не нашёл. Есть половинки: Vul-RAG
  (негативы судье), DAIL-SQL/CHASE-SQL (позитивы генератору). → Это **наша
  потенциальная новизна** (плюс к ВКР), но и риск: проверять только эмпирикой.
- **Утечка между сторами при общих весах** — отдельной работы по «изоляции
  позитив/негатив контекста при gen=judge» не нашёл. Решаем инженерно (§1 ADR).
- **Калибровка суммы risk_score под порог 4.0** в ансамбле — общих рецептов
  мало; делаем сами на eval-сплите.
- **Доменный перенос few-shot** (2510.27675): эффект может быть слабым на
  нашем домене → A/B обязателен, не переносим выводы с C/C++/Python.
